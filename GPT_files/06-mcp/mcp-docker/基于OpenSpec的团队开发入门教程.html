基于 Spec 的开发：团队上手教程

面向已有基础 AI coding 经验的开发成员。用一个真实的小需求，练习从需求澄清到验收归档的完整流程。

目录01 学习目标02 环境准备03 完整流程04 实战示例05 评审与协作06 两周带教安排07 衡量效果08 常见问题

01 · 学习目标

核心变化：先把需求写成团队和 AI 都能验证的约定，再让 AI 实现。

澄清需求→编写 Spec→评审设计与任务→实现→验证→归档
Spec 回答“系统应如何表现”输入、输出、业务规则、边界、异常及可验收场景。
Design 回答“如何实现”接口、模块、数据结构、依赖、迁移和技术取舍。
Tasks 回答“先做哪些事”可执行的步骤、负责人、依赖关系及验证任务。
证据回答“是否真的完成”测试结果、人工验证记录及与 Spec 场景的对应关系。

完成标准：每位成员能独立提交一个包含 Spec、实现和验收证据的小变更，并能解释每条关键业务规则的来源。

02 · 环境准备

  1. 选择一个已有测试且成员熟悉的代码仓库；先定团队约定：需求负责人、评审人、合并负责人。
  2. 安装 Node.js、Claude Code 和 OpenSpec CLI；安装方式与版本以团队当前环境及官方安装说明为准。
  3. 在仓库根目录运行 openspec init，初始化时选择 Claude Code。提交初始化生成的项目文件，确保其他成员使用同一套流程。
  4. 重启 Claude Code，确认能看到 /opsx:propose、/opsx:apply 等命令。

内部模型连接检查

由平台负责人配置网关地址、凭据和模型映射，不在仓库里提交密钥。Claude Code 可通过 ANTHROPIC_BASE_URL 使用网关，但网关需要支持其所需的 Anthropic 消息格式和工具调用；仅提供 OpenAI 兼容接口并不足以保证可用。

# 示意：具体凭据变量、模型映射以内部网关文档为准
export ANTHROPIC_BASE_URL="https://your-internal-gateway.example"
# 通过公司批准的凭据注入方式配置认证
claude

正式带教前跑通一条最短链路：读代码 → 生成变更文档 → 修改文件 → 执行测试。记录模型、网关及 Claude Code 版本，便于复现问题。

03 · 从需求到交付

阶段成员动作人来把关产出
探索阅读现有代码与测试，列出未知规则确认需求来源和边界问题清单
提案运行 /opsx:propose，生成 proposal、spec、design、tasks评审行为、异常和验收场景获批的变更文档
实现运行 /opsx:apply，按任务逐步改动检查改动范围和共享接口代码和必要测试
验证对照 Spec 逐条执行测试，记录结果确认关键场景有证据验收记录与 PR
归档完成变更后运行 /opsx:archive确认文档与实际行为一致当前有效 Spec

终端运行 openspec CLI；/opsx:* 输入在 Claude Code 对话中。生成的文档是草稿，需求负责人应先审阅，再开始实现。

04 · 30–90 分钟实战：给接口增加输入校验

示例需求：创建任务接口的标题不能为空；空白标题返回 400 和约定错误码；失败时不得写入数据库。请用你们仓库里相似的真实接口替换它。

步骤 A：先让 AI 理解现状

请阅读创建任务接口的实现、请求模型和现有测试。
告诉我当前标题校验和错误响应的行为；不要修改代码。
列出需要业务负责人确认的歧义。

步骤 B：生成并评审 Spec

/opsx:propose 为创建任务接口增加标题非空校验。
先基于现有实现写 proposal、spec、design、tasks。
要求覆盖空字符串、仅含空白字符、合法标题、错误响应和数据库无写入。
保持现有其他字段行为；遇到错误码或空白定义不明确时先列出待确认项。

评审时把模糊句子“标题不能为空”改成可检验场景。例如：

场景：标题仅含空白字符
给定：请求中 title = "   "
当：调用创建任务接口
则：返回 HTTP 400 和团队约定的错误码
并且：数据库未新增任务记录

错误码、空白字符处理范围等规则必须由项目既有约定或业务负责人确定；不要让 AI 猜出一套新规则。

步骤 C：实现与验证

/opsx:apply

让成员提交 PR，并在描述中列明：变更对应的 Spec 场景、运行的测试命令、测试结果，以及任何尚未解决的差异。评审通过且变更完成后执行 /opsx:archive。

05 · 评审清单与多人协作

多人并行时怎么拆

先按可独立验收的能力划分变更，再按文件归属分配成员；让一个人负责共享接口和集成。若两个任务都要改同一接口或数据模型，应先共同确认契约和合并顺序，再分支开发。

角色责任
需求负责人确认行为、优先级及验收口径
Spec 负责人维护变更文档、澄清问题、组织评审
实现成员按批准任务实现、补测试、提交证据
集成负责人协调共享文件与接口、完成合并验证

06 · 两周带教安排

时间练习检查点
第 1 天负责人演示一个完整的小变更；成员现场找 Spec 歧义能区分行为描述和实现方案
第 2–3 天两人结对修改 Spec，补异常场景，再实现评审通过后才写代码
第 4–5 天每人独立完成一个小变更PR 中有文档、代码及验收证据
第 2 周一个中等需求，约定共享接口后分工并行能合并、能回归、能归档

每天用 15 分钟复盘：今天哪条规则原本不清楚、在哪个阶段发现、是否导致返工。把团队反复遇到的问题加入 PR 模板和 Spec 评审清单。

07 · 怎么判断真的有效

开始前选取近期相似需求做基线；两周试点后按相同口径比较。不要只统计生成了多少份 Spec。

指标记录方式希望看到的变化
需求澄清往返次数从接单到 Spec 获批的问答轮数随着模板成熟逐步下降
需求理解偏差导致的返工PR 评论或返工单标记原因数量和耗时下降
交付周期Spec 获批到验收完成的时间并行后缩短，且质量不下降
验收覆盖有证据的关键场景 / 关键场景总数逐步接近 100%

目标值应根据你们的项目基线设置；首轮先取得真实数据，再决定是否扩大到整个团队。

08 · 常见问题

很小的改动也要写完整文档吗？

按变更风险调整篇幅。一个小修复可以只有简短行为说明和验收场景；跨模块或涉及外部契约的变更需要更完整的设计与任务拆分。

内部 LLM 生成的 Spec 不可靠怎么办？

先缩小上下文和需求范围，让模型引用现有代码与测试；由人确认业务规则。保留错误样例，区分模型理解、网关兼容性及项目背景缺失。

什么时候开始多人并行？

成员能独立完成一个小变更，且团队已经确定共享接口、代码归属与集成负责人时。先从两个独立模块开始。

Claude Code 看不到 /opsx 命令怎么办？

检查是否在正确仓库执行了 openspec init、是否选择 Claude Code，并重启 Claude Code；再对照 OpenSpec 当前设置文档排查。
