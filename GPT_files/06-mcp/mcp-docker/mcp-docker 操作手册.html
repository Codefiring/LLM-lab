01它是什么

一个控制面。你把一份不受信任的 MCP 服务器源码交给它，它负责把这份源码变成一个你敢跑的东西。

MCP 服务器是别人写的代码，而你要在自己的机器上运行它。直接 npx 起来，它能读你的文件、能联网、能装东西 —— 而且你很难说清它到底做了什么。这个项目要解决的就是这件事：

  • 构建期：在一个没有出网路由的网络里构建，只有你白名单里的包仓库能访问。包的生命周期钩子照样允许执行 —— 约束放在网络层，而不是靠检查命令。
  • 验证期：镜像造出来不算完。起一个一次性容器，真的做一次 MCP 握手；答得对才算这个镜像可用。
  • 运行期：非 root、只读根文件系统、无特权、有 CPU / 内存 / 进程数上限、空闲自动停。stdio 服务器完全没有网络。
  • 对外：不管后端说哪种 MCP 方言，客户端看到的都是同一种 Streamable HTTP。
一句话

它不是一个 MCP 服务器，也不是一个客户端。它是中间那层：把源码变成镜像、把镜像变成服务、并且在这两步上都留下可以被检查的证据。

02一次请求的全程

从你交出源码，到客户端能说话，中间发生五件事。每一步都有自己的失败方式和自己的日志。

1

暂存（staging）

源码被复制成一个不可变的修订，带内容摘要。路径必须落在你配置的白名单目录内，压缩包有体积上限，符号链接和穿越路径会被拒。

2

分析（analyze）

确定性分析器先跑：认 npm / pnpm / yarn / bun / uv / pip 的清单和锁文件，推出语言、安装步骤、构建步骤、启动命令、以及该用哪种就绪探针。推不出来就报缺口，不猜。配了模型的话，会有一层受约束的 LLM 兜底 —— 它只能填空，产物仍然要过 schema 和策略校验。

3

构建（build）

在受限 builder 上构建。出网只到白名单里的主机，由一个出网代理强制执行。缓存按「源码 + 计划 + 锁文件 + 基础镜像 + 策略」取身份。

4

验证（validate）

起一个一次性容器，做一次真实的 MCP 握手。探针跟着 transport 走：stdio 走进程流、Streamable HTTP 走一次 POST、老式 SSE 走它那两条连接。握手不过，镜像不会成为可运行制品。

5

服务（serve）

用受限容器跑起来，网关在 /mcp/{serverId} 上对外。stdio 的会话由网关持有并做请求关联；HTTP 后端自己管会话。

这五步里，构建和启动是异步的：你发一个请求，拿回一张票据（operation id），然后轮询它。 这件事在日常操作那节说清楚。

03五分钟上手

前置条件只有三样：Node ≥ 22.18、Docker、以及两个预先拉好的基础镜像。没有运行时依赖，不需要 build。

第一步：装上、看它是不是好的

git clone <仓库> && cd mcp-docker npm ci docker pull node:24-alpine docker pull python:3.13-slim npm run typecheck # 没有输出就是过了 npm test 2>&1 | tee /tmp/run.txt && ./scripts/assert-suite-complete.sh /tmp/run.txt ℹ tests 1333 ℹ pass 1333 ℹ fail 0 ℹ skipped 0 tests=1333 pass=1333 fail=0 skipped=0 floor=1000

那两个基础镜像是硬前置。用到它们的测试读的是本机 digest，缺了会跳过而不是去拉 —— 所以后面那条断言脚本不能省，它拒绝「有跳过」这种假绿。

第二步：建一次受限构建环境

export MCP_MANAGEMENT_TOKEN=随便一个你自己的串 node --experimental-strip-types src/build/provision.ts deploy/local.json builder mcp-local-builder proxy mcp-local-proxy at http://10.x.x.x:8888 networks mcp-local-internal (no route out), mcp-local-egress allowlist https://registry.npmjs.org, https://pypi.org/simple egress direct

只建一次，不是每次构建都建 —— 层缓存活在那个 builder 身上，每次重建会让所有构建都变冷。拆掉是同一条命令加 --teardown。

第三步：起控制面

node --experimental-strip-types src/main.ts deploy/local.json

两个口：8080 网关、8081 管理（用 MCP_GATEWAY_PORT / MCP_MANAGEMENT_PORT 改）。 启动时它会核对上次遗留的容器 —— 记录说在跑而其实没了的，会被改成 stopped。

第四步：上一个服务，然后跟它说话

# 1. 建配置 curl -s -X POST localhost:8081/api/servers -H "authorization: Bearer $T" \ -H 'content-type: application/json' -d '{ "id":"probe","name":"probe", "source":{"kind":"staged","revision":"pending"}, "transport":{"profile":"stdio"},"auth":{"mode":"none"}}' 201 → 返回里带 "mcpUrl":"/mcp/probe" # 2. 暂存源码（目录必须在 source.allowedRoots 之内） curl -s -X POST localhost:8081/api/servers/probe/source/local -H "authorization: Bearer $T" \ -H 'content-type: application/json' -d "{\"path\":\"$PWD/examples/probe-mcp-server\"}" 201 → revision / digest / fileCount # 3. 构建：拿回的是一张票据，不是结果 curl -s -X POST localhost:8081/api/servers/probe/build -H "authorization: Bearer $T" 202 {"operationId":"8ea7...","kind":"build","state":"running"} # 4. 轮询那张票据直到不是 running，然后 /start，再轮询一次 # 5. 当外部客户端说 MCP curl -si -X POST localhost:8080/mcp/probe -H 'content-type: application/json' \ -H 'accept: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"initialize", "params":{"protocolVersion":"2025-06-18","capabilities":{}, "clientInfo":{"name":"you","version":"1"}}}' mcp-session-id: c12c4bbd-... ← 留住它，后面每个请求都要带 serverInfo: {"name":"probe-mcp-server","version":"1.0.0"}
为什么要留 session id

stdio 服务器只有一个 stdin，所以会话由网关持有 —— 这是「一个服务器同时只服务一个客户端」这条规则的落地方式。HTTP 后端自己管会话，网关不发这个头。

04配置详解

一个 JSON 文件。下面每一行都写了这个字段是干什么的，以及写错或不写会怎样。

两条贯穿全局的规则

  • 凭据永远不写在文件里。文件只写环境变量的名字，所以字段名成对出现：authTokenEnv 收变量名，写成 authToken 放字面值会被直接拒绝。
  • 相对路径按配置文件所在目录解析，不是按进程的工作目录 —— 换个地方启动不会换一个数据库。
写错一个字母会被拒，不会静默取默认

任何一层的未知键都会被拒绝并点名。"resources": { "cpu": 99 } 会报 resources.cpu is not a known configuration field。 这条值得单独说，因为它曾经不成立：未知键只在顶层检查，段内随便写。实测 { "cpu": 99, "memoryByte": 1, "pid": 7 } 曾经加载成功、三个限额全是默认值、一句提示都没有。

最小可用配置：六段

{ "docker": { "socketPath": "/var/run/docker.sock" }, "storage": { "root": "./var/storage" }, "database": { "path": "./var/control-plane.db" }, "source": { "allowedRoots": ["/srv/mcp-sources"] }, "management": { "authTokenEnv": "MCP_MANAGEMENT_TOKEN" }, "gateway": { "externalBaseUrl": "https://mcp.example.com" } }

必填的

字段目的不写 / 写错会怎样
docker.socketPath控制面通过它跟 Docker 守护进程说话：建容器、查镜像、删镜像。指错了会在第一次操作时报连不上。注意它要和你 docker 命令实际用的是同一个守护进程。
storage.root源码修订、构建与运行日志、镜像元数据都放在这下面。这是你要备份的东西之一。
database.path服务配置、构建状态、操作记录的 SQLite 库（Node 内置 sqlite，不是原生模块）。另一个要备份的东西。
source.allowedRoots运维提供的宿主路径只能从这些目录下暂存。这是宿主文件系统的边界。必须至少一个绝对路径。不在白名单内的路径被拒；指向里面的符号链接也拒。
management.authTokenEnv管理 API 的令牌从哪个环境变量读。比较是常数时间的。变量没设 → 加载失败并点名。写成 authToken 放明文 → 拒绝。
gateway.externalBaseUrl客户端从哪里访问到这个部署。鉴权时用它拼出每个服务的 resource 标识。必须是 http/https 且不带路径（路由会被追加上去）。「这个部署在哪」没法猜，所以是必填。

隔离与出网

字段目的默认 / 注意
buildkit.builder构建跑在哪个 buildx builder 上。名字必须以 -builder 结尾，其余部分是整个环境的前缀。不写 = 用默认 builder，那是一张普通网络 —— 构建期出网不受限制。这个字段可选，正是为了让这件事显式。
buildkit.upstreamProxy你的网络本身需要代理才能出去时，出网代理往上游再转一层。它不放宽能访问什么（白名单先生效），只决定被允许的请求怎么出去。是一台机器的事实，不该提交进仓库。
registries.allowlist构建期允许访问的主机。由出网代理强制执行。默认公共 npm 与 PyPI。镜像 registry 也必须在白名单里 —— Docker Hub 的几个主机已经是默认值，换别的镜像仓库要自己列。
command.approvedShells这个部署批准哪些 shell 可以当启动命令。默认空数组 = 一个都不批准。启动命令必须是 argv 数组，shell 字符串会被拒。
source.maxArchiveBytes上传压缩包的体积上限。有默认值；必须是正数。

镜像与资源上限

字段目的默认
images.baseImages每种语言用哪个基础镜像。必须用 digest 锁定（name@sha256:…），而且要用仓库 digest 而不是本地 image id —— 两者都是 64 位十六进制，但只有前者在构建拉取时能解析。
images.keepPerServer一个服务保留多少个镜像。成功构建之后自动回收旧的。3。是总数：写 1 表示「当前镜像和别的都不留」。0 会被拒而不是被解释成 1。
resources.cpus每个容器的 CPU 配额。1
resources.memoryBytes内存上限。536870912（512 MB）
resources.pids进程数上限 —— fork bomb 撞上的就是这道墙。256
resources.buildTimeoutMs一次构建的墙钟上限。900000（15 分钟）
resources.startupTimeoutMs服务器多久之内要答完就绪探针。30000
resources.stopGraceMs收到 SIGTERM 之后、被强杀之前有多久。10000
resources.idleTimeoutMs空闲多久自动停掉。清扫每 30 秒跑一次。600000（10 分钟）
resources.maxLogBytes日志文件上限。1048576（1 MB）
一个已知的设计债

resources.maxLogBytes 同时是 stdio 网桥的最大消息体积。两件无关的事共用一个数字：把日志收紧到 64 KB，就同时把客户端能发的最大 MCP 消息压到 64 KB，而且没法只调一个。这是已记录、未修的。

可选能力

字段目的不写会怎样
auth.contextKeysPath签发「内部身份上下文」的密钥文件。网关校验完客户端令牌后，用它告诉后端「是谁来了」 —— 客户端的令牌本身绝不下传。不写 = 这个部署不签上下文。文件权限必须只有属主可读，否则整个控制面拒绝启动。
secrets.root被托管服务的凭据从这个目录下的文件读（file:NAME 形式的引用）。不写 = 只能用 env:NAME。这个目录不能和 storage 根重叠，否则写进去的文件会被当成机密读出来。
llm.baseUrl · llm.model · llm.apiKeyEnv · llm.timeoutMs确定性分析定不下来时的受约束兜底。模型只能填空，产物仍要过 schema 和策略校验；它给的启动命令不会覆盖你指定的。不写 = 定不下来就停在 needs_input 并逐条列出缺口。
机密绝不落地

机密在捕获那一刻就被脱敏 —— 日志、构建计划、镜像、API 响应里都不会出现。这不是「输出前过滤一遍」，是写入时就替换掉。

05日常操作

所有管理端点要 Authorization: Bearer <token>。网关口（/mcp/…）是另一回事，由每个服务自己的 auth 模式决定。

方法路径做什么
GET POST/api/servers列出全部 / 建一个（id 可省）
GET PUT DELETE/api/servers/{id}读 / 整体替换配置 / 删（连源码、日志、镜像元数据一起带走）
POST/api/servers/{id}/source上传 tar / tar.gz
POST/api/servers/{id}/source/local从宿主目录暂存（必须在白名单根下）
POST/api/servers/{id}/build · rebuildrebuild 忽略缓存
POST/api/servers/{id}/start · stop · restart生命周期，各返回一张票据
GET/api/servers/{id}/runtime · runtime/logs状态问运行时而不是读记录 —— 记录说的是上次写下的，容器可能已经停了
GET/api/servers/{id}/operations这个服务的操作历史
POST/api/servers/{id}/images/prune立刻回收旧镜像。同步返回 200 加走掉的 digest
GET/api/operations/{opId} · {opId}/logs某次操作进行到哪了、它的输出
POST/mcp/{serverId}网关口：外部 MCP 入口

票据模型：为什么不是同步返回结果

构建和启动都要几十秒到几分钟。所以它们返回 202 加一张票据：build、rebuild、start、stop、restart， 以及 DELETE —— 删一个服务要把镜像、源码、日志一起带走，那不是一行记录。

  • 同一个服务同时只有一个在飞的操作。构建时再来一个请求，返回的是正在跑的那个，不会并发两次构建。
  • 正在运行的服务删不掉（409），先停。一个服务从客户端脚下消失，不是有人说 DELETE 时要求的。
  • 操作报完成时，事情真的做完了。启动的票据在容器真的在跑之后才变 succeeded，而不是镜像就绪时。
  • PUT 只是替换配置，同步 200。images/prune 是另一个例外：它就是几次删除，给票据会让你为一件已经做完的事轮询。

日志分三处，不混

看什么去哪里
构建输出（为什么构建失败）GET /api/operations/{opId}/logs
运行输出（服务自己打印了什么）GET /api/servers/{id}/runtime/logs
协议流量不作为日志提供 —— 它是流

构建失败时，先读构建日志。它会说清是哪一步、什么原因，包括出网被拒时代理自己的那句话。

06三种 transport

对外永远是一种协议（Streamable HTTP）。内部三档，由每个服务的 transport.profile 指定。

profile后端长什么样网关做什么网络
stdio读写标准输入输出的进程，换行分隔的 JSON-RPC持有会话、做请求关联、桥接 stdio无网络
streamable-http自己在容器里听一个端口，现代 MCP HTTP反向代理过去，后端自己管会话bridge
legacy-http-sse2024-11-05 的老式两连接：一条 SSE 流宣告投递地址，POST 发到那个地址，答案从流上回来兼容层：把两条连接折叠成对外的一条bridge
HTTP 档案的代价，是量出来的

HTTP 后端必须被网关访问到，所以它在一张 bridge 网络上 —— 而那同时意味着它能出网。这是这个 profile 的代价，不是疏漏：它在验证里是一个被测量的数字，而不是文档里的一句话。stdio 的服务器则是真的没有网络。

就绪探针跟着 transport 走。这件事曾经不成立：两个 HTTP 档案共用一个 Streamable 形状的探针，于是一个老式 SSE 服务器会构建成功、校验超时、报别人的 404 —— 能被服务，却造不出来。

07三种鉴权模式

每个服务在自己的配置里写 auth.mode。区别在于「客户端的令牌会不会到达后端」。

mode网关做什么后端看到什么什么时候用
none不校验什么都没有本机、可信网络内
gateway-oauth按 OIDC 校验客户端令牌（discovery → JWKS → RS256 → iss/aud/exp）一个签名的身份上下文，说明是谁来了。客户端的令牌绝不下传。绝大多数情况
backend-passthrough校验之后，把客户端自己的令牌转给后端客户端的原始 Bearer 令牌后端必须拿原令牌去调第三方 API 时。只有 HTTP 后端能收 —— stdio 配这个模式会被拒

配 gateway-oauth 需要 issuer（必须 https）。resource 可以不写，写了就必须和这个部署的 gateway.externalBaseUrl 加这个服务的路由对得上 —— 写成别的服务的路由会被拒，而且错误信息会同时点出两个值，否则运维不知道该改哪一个。

这条链路是对着一个真实的身份提供方（本地 Dex）跑通的，不是假 IdP。那一轮找出了三个缺陷，其中一个是 API 接受了 http:// 的 issuer、存了下来，然后网关在第一个受保护请求上以 500 拒绝它 —— 两套 auth 规则各说各话。

08隔离到什么程度

仓库里的示例服务器自带探测工具，专门为了让你从容器里面验这些声明 —— 比 docker inspect 强，因为这是服务自己的视角。

调用这个工具会看到它证明了
whoamiuid 10001, gid 10001, root: false不是 root
write-probe {"path":"/x"}writable: false, reason: EROFS只读根文件系统
write-probe {"path":"/tmp/x"}writable: true只有 /tmp 能写
net-probereached: falsestdio 档案完全没有网络
hook-markerran: true构建期的 postinstall 钩子执行过
最后一条是设计立场

包的生命周期钩子是允许执行的。约束放在网络层，而不是靠检查命令 —— 钩子跑了，但它当时只能访问白名单里的主机。想靠「禁止钩子」来保证安全，是把约束放在了一个绕得过去的地方。

构建期的出网限制同样可以自己验：从那张没有出网路由的内部网络里发真实 CONNECT，白名单内的主机是 200 Connection Established，白名单外的是 403 Forbidden，而不走代理时连 DNS 都解不了。

09怎么验证它没坏

六层，代价从低到高，每层用不同的前置条件、证明不同的事，任何一层都可以停。

层命令要什么证明什么
类型npm run typecheck只要 Node几条由类型守的规则没被绕开
套件npm test + 完整性断言Docker + 两个基础镜像1333 条，含真镜像真容器
分析verify:real -- --static网络9 个真实第三方仓库能被分析器认出
真实verify:realDocker + 网络 + 十几分钟9/9 走完整条路并通过网关对话
运维手动跑一遍控制面以上全部唯一能看到运维视角的一层
接线assert-config-wired.tsDocker + 约 12 分钟「值错了会不会有东西红」
最后一层问的是一个不同的问题

不是「有没有测试」，而是「把这个值改错，会不会有东西红」。第一次跑它的结果是：25 条线里 10 条没有任何测试守着，其中两条是安全性质。 这两个问题的距离，就是「有一条测试通过了，但它在任何取值下都通过」所在的地方。

npm test 后面那条完整性断言不能省：它拒绝三种假绿 —— 有失败、有跳过、总数低于下限。 跳过算假绿，因为有些测试缺镜像时跳过而不是去拉，于是一个没拉的 tag 就是一个无声的缺口。

10新机器上的三个坑

这三样都是在真实的新机器上踩出来的，不是设想的。

一、到不了 Docker Hub

构建会停在 FROM node@sha256:…，报 unexpected EOF 或超时。这不一定是白名单的问题 —— Docker Hub 的主机已经在默认白名单里。代理会说清是哪一种：

它的回答意思去改哪里
403 + x-mcp-egress: allowlist白名单拒的registries.allowlist
502 + x-mcp-egress: origin网络到不了buildkit.upstreamProxy

这两种以前都是同一个结果（沉默），所以两个该改不同文件的问题长得一模一样。

一个容易把人骗住的细节

想手工验代理时，busybox 的 wget 对 https 目标不走 CONNECT，它会让每个主机都返回 400，包括白名单内的 —— 看起来像白名单坏了。 「全都失败」和「白名单生效」长得不一样，但同样容易被当成后者。

二、基础镜像没拉

症状是 skipped > 0 而不是红。那条完整性断言脚本存在就是为了把它变成一次失败。

三、CLI 和 socket 不是同一个守护进程

docker 命令走的是 docker context，而配置里的 docker.socketPath 是一个固定路径。 两者不一致时，用 CLI 建的镜像控制面看不见。仓库里有一个脚本专门分辨这类问题，它会依次问：CLI 走哪个端点、配置用哪个 socket、CLI 建的镜像出不出来、那个 socket 看不看得见刚建的镜像。

磁盘

一次通过的测试运行不留镜像（数过，净增 0）。但被打断的运行会留，而且是真镜像不是悬空标签，每个约 170 MB。 在一台折腾了一天、期间多次中途打断的机器上，累计到了 125 个、约 22.5 GB。

不要无脑清掉所有带 mcp.server 标签的镜像。 验证集的镜像清掉只是下次重建变慢，但你自己跑起来的服务的镜像是当前镜像，删了那个服务就起不来了。 正规办法是走 API：DELETE /api/servers/{id}，它会连源码、日志、镜像元数据一起带走。

被托管服务的容器不随控制面停止而消失 —— 那是有意的：控制面重启后会把它们认回来。 控制面自己的数据在 storage.root 和 database.path 指的地方，这两样是你要备份的。

这份页面上的每个数字和每段输出，都来自在一台机器上真的跑过一遍。 数字会随变更增长 —— npm test 的输出才是权威，这里写的是「那一刻」。 仓库里有更细的几份：部署与 API 的完整参考、每条安全性质对应到证明它的测试、每个配置字段对应到会红的那条测试、以及在一台新机器上从头验一遍的分阶段手册。
