用 Superpowers
从零完成一个小项目

一份给已有基础 AI Coding 经验的开发者的简易教程。从空目录出发，跟做一个 MCP 工具清单静态检查器，走通需求、设计、计划、实现和验收。

适用：Claude Code + Superpowers练习约 90–150 分钟单人上手

01 · 这次要做出的东西

你手里没有现成代码仓库。我们从空目录开始，做一个可运行的小工具：读取一份 MCP 工具清单 JSON，找出缺失描述、工具名重复、输入 Schema 不是对象的情况，并生成 JSON 报告。

空目录→定义规则→审阅计划→写测试→写程序→验收报告

这个项目足够具体，可以检验 Superpowers 是否真正按设计、计划、测试和验证推进；检查结果仅是清单质量提示，不等于发现安全漏洞。

交付物

audit.py：命令行程序；examples/tools.json：练习输入；tests/test_audit.py：自动化测试；report.json：运行后生成的报告；README.md：运行说明。

02 · 准备环境与安装插件

需要 Python 3.10+、Git、能读写本地目录的 Claude Code。你们已有的内部模型接入继续沿用；本教程只关注 Superpowers 开发流程。先分别运行 python --version、git --version 检查环境，Windows 可将后续 Python 命令改成 py。

Claude Code 中的安装命令
/plugin install superpowers@claude-plugins-official

安装完成后开启新会话。若企业环境无法访问插件市场，按组织允许的方式安装。打开新会话后，向它提出建一个小应用的任务，观察它是否先讨论需求和设计，而非直接输出大量代码。

技能流程和安装命令依据官方仓库 2026 年 9 月 28 日的文档；具体界面和自动调用方式以已安装版本为准。

03 · 从空目录创建练习项目

你只需准备一个空目录和 Git 初始提交。源码、测试和样例文件都在后面的 Superpowers 流程中创建。

终端操作
mkdir mcp-tool-audit-lab
cd mcp-tool-audit-lab
git init
git commit --allow-empty -m "Initialize empty audit project"
claude

若 Git 报缺少身份，先按平时方式设置用户名和邮箱。这里的 --allow-empty 是空提交，不会预置任何代码。

给练习提供一份确定的输入

下面是稍后要让 Claude 创建的 examples/tools.json 的精确内容。它是一份教学用工具清单，不需要连接任何 MCP 服务器，也不会执行里面的工具。

examples/tools.json · 在设计确认后由 Claude 创建
{
  "server": "demo-files",
  "tools": [
    {
      "name": "read_file",
      "description": "Read a text file",
      "inputSchema": {"type": "object", "properties": {"path": {"type": "string"}}}
    },
    {
      "name": "delete_file",
      "description": "",
      "inputSchema": {"type": "array"}
    },
    {
      "name": "delete_file",
      "description": "Delete a file",
      "inputSchema": {"type": "object", "properties": {"path": {"type": "string"}}}
    }
  ]
}

样本特意设置了 3 个问题：第 2 个工具缺少描述、其输入 Schema 的 type 不是 object、第 3 个工具与第 2 个同名。先有固定输入和固定结果，后面才能判断开发是否符合需求。

04 · 用 Brainstorming 确认规则

在空目录中启动 Claude Code 后，先发需求。让它讨论规则与边界，并在你确认前不写程序。

提示词 A · 启动项目
当前目录只有一个空 Git 提交。请使用 Superpowers 的 brainstorming 流程，
从零做一个 Python 命令行工具：读取 MCP 工具清单 JSON，执行静态检查，
输出机器可读的 JSON 报告。请先梳理输入格式、检查规则、输出格式、
错误处理和测试策略；我确认设计后再创建源码和样例。

它会提出设计问题。请用下面这组具体约束回答，避免“检查工具安全性”这种难以验收的宽泛任务。

提示词 B · 明确范围与验收口径
本练习的设计约束：
1. 只用 Python 3.10+ 标准库，不联网，不启动 MCP Server，不调用任何工具。
2. 输入是 JSON 文件：顶层对象有 server 字符串与 tools 数组；
   每个工具是对象，包含 name、description、inputSchema。
3. 对 tools 按数组顺序检查，仅做三条规则：
   MISSING_DESCRIPTION：description 不是非空字符串，或仅有空白。
   DUPLICATE_NAME：当前工具的 name 与前面某工具重复；只标记后出现的项。
   INVALID_INPUT_SCHEMA：inputSchema 不是对象，或 type 不等于 "object"。
4. 每个发现记录 rule、tool、index（从 0 开始），固定顺序：
   对每个工具依次检查上述三条规则，再检查下一个工具。
5. 命令为 python audit.py examples/tools.json --output report.json。
   输出 JSON 包含 server、tool_count、finding_count、findings。
   允许有发现时退出码仍为 0；输入文件不存在或 JSON 不合法时退出码 2，
   向 stderr 给出可读错误，不生成报告。
6. 请创建 examples/tools.json，内容采用我在教程中给出的三工具样本。
7. 本次不做真实协议交互、漏洞判定、风险评级、图形界面或数据库。
请先整理设计供我确认，不要直接编码。

将上节的 JSON 样本粘贴给 Claude。重点检查它是否正确区分“重复项只报后出现者”和“同一个工具可以有多个发现”。确认后回复：设计确认，可以写实施计划。

边界要说清

inputSchema.type == "object" 是本练习自定义的质量检查规则，并不等于对全部 JSON Schema 或 MCP 协议做完整合规验证。不要把报告称作漏洞扫描报告。

05 · 审阅一份能执行的计划

提示词 C · 请求 Writing Plans
设计确认。请使用 superpowers:writing-plans 为这个空仓库写实施计划。
逐项说明新建哪些文件、每项测试的数据与断言、运行命令和预期结果。
先给我审阅计划；我确认前不要实现。
计划任务应看到的内容验证点
1. 输入与数据结构创建样本 JSON、建立 audit.py 的最小入口、添加读取测试能读取三条工具；坏 JSON 显示错误
2. 三条检查规则逐条测试缺描述、重名、Schema；再测试同一项多个发现本例按固定顺序恰好产生 3 个发现
3. CLI 与报告测试 --output、字段、退出码、stderr报告稳定可读，坏输入不生成文件
4. 文档与收尾README 使用说明、全量测试、手工验收、diff 检查没有额外依赖或联网逻辑

审阅重点：计划是否写明具体文件与断言；是否将三个发现的顺序写清；是否包含无效 JSON 和不存在文件的失败路径。若它计划“再接入真正的 MCP Server”或“添加安全评分”，请它删掉。本例只需一条本地数据流。

审阅后明确回复：计划确认，请按计划实施。 官方流程通常要求你看过计划再运行，不把“设计确认”自动视为“计划确认”。

06 · 跟着开发过程看证据

提示词 D · 让它实施
计划确认，请按 Superpowers 流程实施。
每个检查规则先写会失败的测试并运行，确认失败原因正确；
再写最小代码使测试通过。完成后运行全部测试，并给出实际输出。
若测试因语法、导入或环境错误失败，先修复测试本身。

你应看到几次清楚的“红 → 绿”：例如尚未实现 DUPLICATE_NAME 时，重复名称测试因缺少该发现而失败；实现规则后通过；原有测试仍通过。空仓库初期的导入错误只有在建立最小入口过程中有意义，不能替代每条业务规则的失败测试。

本样本的准确期望结果

所有工具按顺序扫描，每个工具按“缺描述 → 重名 → Schema”判断。第 0 个工具无发现；第 1 个触发缺描述和无效 Schema；第 2 个触发重名。因此报告中的 findings 应是：

report.json · 核心内容
{
  "server": "demo-files",
  "tool_count": 3,
  "finding_count": 3,
  "findings": [
    {"rule": "MISSING_DESCRIPTION", "tool": "delete_file", "index": 1},
    {"rule": "INVALID_INPUT_SCHEMA", "tool": "delete_file", "index": 1},
    {"rule": "DUPLICATE_NAME", "tool": "delete_file", "index": 2}
  ]
}

测试至少应包含：这个样本的 3 个发现和顺序；无问题数据的空发现；仅空白字符的描述；重复名称只标记后项；Schema 缺失或 type 错误；文件不存在与 JSON 格式错误；有发现时退出码为 0。让 Claude 用临时目录写测试文件，避免污染练习目录。

如果实现卡住，查看一个最小算法轮廓
seen = set()
findings = []
for index, tool in enumerate(tools):
    name = tool.get("name")
    if not isinstance(tool.get("description"), str) or not tool["description"].strip():
        findings.append({"rule": "MISSING_DESCRIPTION", "tool": name, "index": index})
    if name in seen:
        findings.append({"rule": "DUPLICATE_NAME", "tool": name, "index": index})
    seen.add(name)
    schema = tool.get("inputSchema")
    if not isinstance(schema, dict) or schema.get("type") != "object":
        findings.append({"rule": "INVALID_INPUT_SCHEMA", "tool": name, "index": index})

算法片段只用于解释设计，不处理顶层结构、参数解析和文件错误；完整实现仍应遵循你已确认的计划与测试。

07 · 自己验收这个具体项目

实现结束后，在项目目录运行下面的命令。这里检查的是真实生成的报告文件，而不是 Claude 口头描述的结果。

命令行验收
python -m unittest discover -s tests -v
python audit.py examples/tools.json --output report.json
python -m json.tool report.json
git diff --check
git status --short

查看 report.json，其 server 应为 demo-files、tool_count 为 3、finding_count 为 3；三个发现的规则与索引必须与上节一致。运行 python audit.py does-not-exist.json --output missing-report.json，应看到清楚的错误，退出码为 2，且不出现 missing-report.json。

提示词 E · 让它报告实际执行记录
请只报告实际执行的命令和结果：测试用例数、示例报告的
finding_count 和三条规则顺序、坏输入的退出码、改动文件。
列出尚未验证的情况，检查 git diff --check 与最终变更。
  • 从空目录生成了 audit.py、样本、测试与 README
  • 本例得到 3 个发现，顺序和 index 都正确
  • 正常输入退出码 0，错误输入退出码 2 且不产生报告
  • 看到每条规则先失败再通过的测试证据
  • 没有联网、执行工具、风险评级或额外依赖

08 · 本练习常见偏差

把质量检查说成漏洞扫描

这三条规则只评价清单字段，不能证明攻击可行性，也不能替代动态验证。

发现数量对、顺序错

只看 finding_count=3 还不够；同一工具可能有两个发现，必须检查规则、工具名、索引与顺序。

意外扩展项目

让它回到本地 JSON 的输入与输出，先完成一个能可靠运行的 CLI，再决定是否扩展真实 MCP 接入。

红灯原因不对

SyntaxError、测试导入错误或样本路径错误要先修复；真正的“红灯”应由尚未实现的业务行为引起。

如果没有触发技能，重启会话并检查插件安装；必要时明确写“使用 superpowers:brainstorming”。
