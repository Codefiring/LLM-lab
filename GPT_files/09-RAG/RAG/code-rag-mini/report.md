# 公司内部代码库 RAG 系统应用报告

---

## 1. Background / Pain point

公司内部虽然已经搭建了自研的大模型服务，但目前缺乏配套的 **RAG（Retrieval-Augmented Generation）服务**。这带来几个关键痛点：

1. **无法高效利用代码库**：

   * 工程师在日常工作中会频繁遇到“如何调用某个模块”、“这个函数在哪里被实现”等问题。过去往往只能依赖 IDE 的全文检索，或手动打开多个文件逐行查找，效率低下。
   * 随着代码库规模的扩大，知识沉淀日益分散，新人学习成本高，老员工也难以及时定位到历史实现细节。

2. **缺乏与大模型的结合**：

   * 内部大模型只能回答通用问题，缺乏和代码上下文结合的能力。
   * 即便大模型可以编写代码片段，它也无法理解企业内部的业务框架和已有实现，容易生成与现有系统不兼容的答案。

3. **工具门槛高**：

   * 缺少统一的可视化工具来结合大模型与代码库。
   * 工程师需要手动准备上下文，才能让模型做出有限的帮助。

这些问题直接导致知识无法充分复用，沟通与学习成本增加，研发效率受限。

---

## 2. Goal

项目的目标是为公司内部搭建一套 **轻量级、易用、可落地的 RAG 系统**，具体包括：

* **为内部大模型提供 RAG 层**：通过语义检索补充上下文，让模型能结合公司代码库回答问题。
* **降低使用门槛**：提供直观的 Web 前端界面，支持一键检索与问答，工程师无需命令行即可操作。
* **支持多场景**：既能处理工程师的日常开发问答，也能用于新员工培训、代码审查辅助、架构理解等场景。
* **保证可扩展性**：后续可以支持跨仓库、跨团队的统一检索，逐步形成公司级知识库。

---

## 3. Method

实施方式主要分为三个阶段，每个阶段都有明确的成果产出。

### 阶段一：核心能力开发

* **实现内容**：

  * 使用 `rag_code.py` 对代码库进行递归解析，将代码按行切片并进行语义向量化。
  * 构建 FAISS 向量数据库，支持高效的 Top-K 检索。
  * 实现 RAG Prompt 拼接逻辑，让模型能够在回答时结合检索结果。
* **阶段性成果**：完成了命令行版本工具，用户可以在本地对代码库建索引，并基于问题进行问答。

### 阶段二：Web Server + API 层

* **实现内容**：

  * 使用 FastAPI 构建后端服务，提供统一的 HTTP API（包括 `/api/build`、`/api/query`、`/api/ask`）。
  * 支持接入内部大模型推理服务，方便未来与更多模型对接。
  * 增加索引状态查询接口，便于管理员了解索引构建情况。
* **阶段性成果**：实现了一个后端服务层，成为前端和内部大模型之间的桥梁。

### 阶段三：前端页面开发

* **实现内容**：

  * 使用原生 HTML + JS 构建简洁的控制台页面。
  * 功能包括：

    1. **索引构建**：用户输入代码目录即可一键构建索引。
    2. **相似检索**：输入问题后，页面展示相关代码片段及路径信息。
    3. **RAG 问答**：结合检索片段，调用内部大模型服务，生成带引用的回答。
  * 前端交互设计简洁直观，支持后续替换为更复杂的 React/Tailwind 页面。
* **阶段性成果**：形成了一个图形化的入口，用户可视化使用系统功能，大幅降低了使用门槛。

## 4. 实施效果和收益

通过对比 **As-Is（改善前）** 与 **To-Be（改善后）**，效果显著：

### As-Is（改善前）

* 工程师只能依赖 IDE 搜索或人工查阅，效率低。
* 大模型只能回答与项目无关的通用问题。
* 知识沉淀分散，新员工学习门槛高。
* 缺乏可视化工具，体验不佳。

### To-Be（改善后）

* 工程师可以自然语言提问，快速检索相关代码片段。
* 大模型能结合代码上下文，生成更准确的解答，并附带引用来源。
* 界面友好，工程师和非技术人员都能快速上手。
* 团队知识得到集中化管理与复用，新人培训周期缩短。
* 整体研发效率提高，减少重复劳动。

---

## 5. Difficulties

在实施过程中遇到以下困难及应对方案：

1. **模型推理延迟**：内部大模型响应时间较长。
   → 方案：结合缓存与检索结果复用，减少重复请求；未来可探索模型量化和蒸馏。

2. **大规模代码库处理**：一次性索引耗时过长。
   → 方案：支持模块化索引和增量更新，避免每次全量构建。

3. **上下文窗口限制**：大模型无法处理过长输入。
   → 方案：采用 Top-K 检索 + 分片策略，必要时可引入重排模型提高上下文质量。

4. **前端交互的直观性**：如何让用户理解检索结果和模型回答的对应关系。
   → 方案：增加代码片段引用标记，清晰展示模型回答与上下文之间的映射。

---

## 6. Others

* **经验总结**：实践表明，轻量级 RAG 系统搭建并不复杂，核心在于分片策略与可用性设计。系统从命令行演进到可视化界面，极大提升了易用性。
* **扩展方向**：未来可支持跨仓库检索、代码与文档混合问答、安全审计等高级功能。
* **启示**：内部大模型若缺乏配套的 RAG 服务，价值会大打折扣。通过构建这样的系统，模型才能真正应用于业务场景，释放其生产力潜力。
