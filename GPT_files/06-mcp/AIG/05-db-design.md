# 数据库设计文档

**项目名称：** MCP Scan 安全扫描平台
**数据库名称：** `mcp_scan.db`
**数据库类型：** SQLite
**版本：** V1.0

## 1. 文档目的

本文档用于说明 MCP Scan 安全扫描平台数据库的整体设计方案，包括数据库选型、表结构设计、字段定义、索引设计、约束关系、核心操作流程以及系统启动恢复机制等内容，为后续开发、联调、维护和扩展提供统一依据。本文档基于当前扫描任务管理、阶段进度跟踪、漏洞结果持久化以及 LLM 配置管理等业务需求进行设计。

## 2. 设计目标

本数据库设计主要服务于以下业务目标：

1. 支持 LLM 服务配置的统一存储与默认配置管理。
2. 支持一次“开始扫描”对应一个顶层扫描任务，并可跟踪任务整体状态。
3. 支持一个任务下多个扫描目标的独立管理与顺序执行。
4. 支持对每个扫描目标的多阶段执行过程进行实时记录。
5. 支持对扫描产生的漏洞结果进行结构化存储。
6. 支持前端通过 SSE 获取任务实时状态，并在断线重连后从数据库恢复完整任务状态。 

## 3. 数据库选型说明

本系统选用 **SQLite** 作为本地数据库引擎，数据库文件名为 `mcp_scan.db`。SQLite 适用于本项目单机部署、本地工具化使用和轻量级持久化场景，具备部署简单、零运维、事务支持完整等特点。数据库启动后启用如下配置：

* `PRAGMA journal_mode = WAL`：开启 WAL 模式，以增强读写并发能力。
* `PRAGMA foreign_keys = ON`：启用外键约束，保证数据引用完整性。

## 4. 总体数据模型设计

系统数据库围绕“扫描任务”主线进行设计，主要包含五类核心实体：

* `llm_profiles`：LLM 服务配置表，用于替代原有 JSON 配置文件。
* `tasks`：扫描任务主表，对应一次完整扫描。
* `task_targets`：扫描目标表，对应任务内每一个 URL 或目标对象。
* `task_stages`：扫描阶段表，用于记录每个目标在各阶段的执行进度与输出。
* `vulnerabilities`：漏洞结果表，用于存储扫描发现的漏洞项。

整体上形成如下层级关系：

* 一个 LLM 配置可被多个任务引用；
* 一个任务可包含多个扫描目标；
* 一个扫描目标可对应多个扫描阶段；
* 一个扫描目标可关联多个漏洞结果。

## 5. 表结构设计

---

## 5.1 LLM 配置表 `llm_profiles`

该表用于存储系统可用的 LLM 服务配置，替代原先的 `llm_profiles.json` 文件。每条记录代表一个可供扫描任务使用的模型服务配置。

### 表结构

| 字段名          | 类型      | 是否为空 | 说明               |
| ------------ | ------- | ---: | ---------------- |
| `id`         | TEXT    |    否 | 主键，LLM 配置唯一标识    |
| `name`       | TEXT    |    否 | 配置名称，要求唯一        |
| `base_url`   | TEXT    |    否 | LLM 服务地址         |
| `api_key`    | TEXT    |    否 | API Key，本地明文存储   |
| `model`      | TEXT    |    否 | 模型名称             |
| `is_default` | INTEGER |    否 | 是否默认配置，0/1 表示布尔值 |
| `created_at` | TEXT    |    否 | 创建时间，ISO 8601 格式 |

### 设计说明

该表主要用于维护扫描所依赖的大模型服务信息。字段 `name` 设置唯一约束，避免重复配置；`is_default` 用于标识默认模型；`created_at` 统一使用 ISO 8601 时间格式，便于展示与排序。由于当前系统定位为本地工具，`api_key` 以明文方式保存在数据库中。

---

## 5.2 扫描任务表 `tasks`

该表为系统的任务主表，每点击一次“开始扫描”即生成一条任务记录，用于记录任务整体状态、关联的模型快照及运行时信息。

### 表结构

| 字段名                  | 类型      | 是否为空 | 默认值       | 说明                                            |
| -------------------- | ------- | ---: | --------- | --------------------------------------------- |
| `id`                 | TEXT    |    否 | -         | 主键，任务唯一标识                                     |
| `status`             | TEXT    |    否 | `pending` | 任务状态：`pending`/`running`/`completed`/`failed` |
| `created_at`         | TEXT    |    否 | -         | 创建时间                                          |
| `completed_at`       | TEXT    |    是 | NULL      | 完成时间                                          |
| `llm_profile_id`     | TEXT    |    是 | NULL      | 关联的 LLM 配置 ID                                 |
| `llm_profile_name`   | TEXT    |    否 | -         | 任务创建时的 LLM 配置名称快照                             |
| `llm_model`          | TEXT    |    否 | -         | 任务创建时的模型名称快照                                  |
| `prompt`             | TEXT    |    否 | `''`      | 用户输入提示词                                       |
| `language`           | TEXT    |    否 | `zh`      | 输出语言                                          |
| `has_oauth`          | INTEGER |    否 | `0`       | 是否启用 OAuth                                    |
| `current_target_idx` | INTEGER |    否 | `0`       | 当前执行到的目标序号                                    |
| `log_file`           | TEXT    |    是 | NULL      | 日志文件绝对路径                                      |
| `error`              | TEXT    |    是 | NULL      | 任务异常信息                                        |

### 设计说明

任务表一方面负责任务生命周期管理，另一方面保留与模型配置相关的快照字段，例如 `llm_profile_name` 和 `llm_model`。这样即使后续配置表中的原始模型记录被删除，历史任务仍可准确展示当时所使用的模型信息。`llm_profile_id` 外键采用 `ON DELETE SET NULL`，确保配置删除不影响历史任务的可追溯性。

---

## 5.3 任务目标表 `task_targets`

该表用于记录一个扫描任务中的每一个扫描目标。一个任务可以对应多个 URL，每个 URL 单独形成一条目标记录，并可分别维护状态、评分、阶段输出及异常信息。

### 表结构

| 字段名          | 类型      | 是否为空 | 默认值       | 说明                                            |
| ------------ | ------- | ---: | --------- | --------------------------------------------- |
| `id`         | TEXT    |    否 | -         | 主键，目标唯一标识                                     |
| `task_id`    | TEXT    |    否 | -         | 所属任务 ID                                       |
| `position`   | INTEGER |    否 | -         | 目标在任务中的顺序，从 0 开始                              |
| `name`       | TEXT    |    是 | NULL      | 目标显示名称                                        |
| `url`        | TEXT    |    否 | -         | 扫描目标地址                                        |
| `stage_ids`  | TEXT    |    是 | NULL      | 阶段 ID JSON 数组，例如 `"[2,5,11]"`，为空表示全部阶段        |
| `status`     | TEXT    |    否 | `pending` | 目标状态：`pending`/`running`/`completed`/`failed` |
| `score`      | INTEGER |    是 | NULL      | 扫描评分，范围 0-100                                 |
| `readme`     | TEXT    |    是 | NULL      | 信息收集报告 Markdown                               |
| `started_at` | TEXT    |    是 | NULL      | 开始时间                                          |
| `ended_at`   | TEXT    |    是 | NULL      | 结束时间                                          |
| `error`      | TEXT    |    是 | NULL      | 扫描异常信息                                        |

### 设计说明

该表体现一个任务对多个扫描目标的管理能力。`position` 用于维持前端展示和执行时的顺序一致性。`stage_ids` 采用 JSON 数组字符串存储，以支持用户按需选择部分扫描阶段执行；若为空，则表示执行系统预设的全部阶段。评分、报告、时间和异常信息均针对单个目标独立记录。`task_id` 外键采用 `ON DELETE CASCADE`，即任务删除时自动删除其所有目标记录。

---

## 5.4 任务阶段表 `task_stages`

该表记录每个扫描目标在各个阶段的执行状态和输出内容，是实现扫描进度可视化与阶段结果追踪的关键数据表。

### 表结构

| 字段名              | 类型      | 是否为空 | 默认值       | 说明                                           |
| ---------------- | ------- | ---: | --------- | -------------------------------------------- |
| `id`             | TEXT    |    否 | -         | 主键，阶段记录唯一标识                                  |
| `task_target_id` | TEXT    |    否 | -         | 所属扫描目标 ID                                    |
| `stage_id`       | INTEGER |    否 | -         | 阶段编号，范围 1–27                                 |
| `name`           | TEXT    |    否 | -         | 阶段名称                                         |
| `status`         | TEXT    |    否 | `pending` | 阶段状态：`pending`/`running`/`completed`/`error` |
| `output`         | TEXT    |    否 | `''`      | 阶段输出内容，Markdown 格式                           |
| `updated_at`     | TEXT    |    是 | NULL      | 最后更新时间                                       |

### 设计说明

系统为每个目标预生成多个阶段记录，以支持细粒度进度展示。扫描运行过程中，后台监控线程会根据日志解析结果实时更新该表中对应阶段的状态与输出内容。通过 `task_target_id + stage_id` 可快速定位某个目标的具体阶段进度。该表外键采用 `ON DELETE CASCADE`，确保删除目标时关联阶段同步清理。 

---

## 5.5 漏洞结果表 `vulnerabilities`

该表用于记录扫描过程输出的结构化漏洞结果。一条扫描目标可关联多条漏洞记录。

### 表结构

| 字段名              | 类型   | 是否为空 | 说明                                          |
| ---------------- | ---- | ---: | ------------------------------------------- |
| `id`             | TEXT |    否 | 主键，漏洞唯一标识                                   |
| `task_target_id` | TEXT |    否 | 所属扫描目标 ID                                   |
| `title`          | TEXT |    否 | 漏洞标题                                        |
| `description`    | TEXT |    是 | 漏洞描述，Markdown                               |
| `risk_type`      | TEXT |    是 | 风险类型，如 `Command Injection`、`CWE-78`、`MCP01` |
| `level`          | TEXT |    是 | 风险等级，如 `High`、`高危`、`Medium`、`中危` 等          |
| `suggestion`     | TEXT |    是 | 修复建议，Markdown                               |

### 设计说明

漏洞表用于最终结果沉淀，支撑前端漏洞明细展示、风险类型分类和修复建议查看。`description` 与 `suggestion` 使用 Markdown 存储，以提升展示灵活性。外键同样采用 `ON DELETE CASCADE`，保证目标记录删除时对应漏洞同步清除。

## 6. 索引设计

为提高列表查询、详情加载和阶段更新效率，系统设计了如下索引：

| 索引名称                | 作用对象                                    | 说明               |
| ------------------- | --------------------------------------- | ---------------- |
| `idx_tasks_created` | `tasks(created_at DESC)`                | 支持任务列表按创建时间倒序展示  |
| `idx_tasks_status`  | `tasks(status)`                         | 支持按任务状态筛选        |
| `idx_targets_task`  | `task_targets(task_id, position)`       | 提升任务详情页按顺序加载目标效率 |
| `idx_stages_target` | `task_stages(task_target_id, stage_id)` | 提升阶段状态更新及查询效率    |
| `idx_vulns_target`  | `vulnerabilities(task_target_id)`       | 提升目标漏洞列表查询效率     |

索引设计充分围绕“任务列表、任务详情、阶段更新、漏洞展示”四类核心读写场景展开，兼顾查询性能与写入复杂度。

## 7. 外键与约束设计

系统通过外键机制维护实体之间的层级关系，并根据业务场景选择适当的删除策略：

* `tasks.llm_profile_id` → `llm_profiles.id`，删除策略为 `ON DELETE SET NULL`。
  含义是：若某个 LLM 配置被删除，历史任务仍然保留，但引用字段置空。

* `task_targets.task_id` → `tasks.id`，删除策略为 `ON DELETE CASCADE`。
  含义是：删除任务时，其下所有目标同步删除。

* `task_stages.task_target_id` → `task_targets.id`，删除策略为 `ON DELETE CASCADE`。
  含义是：删除扫描目标时，其阶段记录同步删除。

* `vulnerabilities.task_target_id` → `task_targets.id`，删除策略为 `ON DELETE CASCADE`。
  含义是：删除扫描目标时，其漏洞结果同步删除。

此外，数据库写操作统一要求使用参数化查询，即采用 `?` 占位符形式，禁止字符串拼接 SQL，以降低注入风险并提高代码可维护性。

## 8. 数据访问设计

系统采用统一的数据库上下文管理方式访问 SQLite。数据库连接初始化时设置：

* `row_factory = sqlite3.Row`，便于字段名访问；
* `PRAGMA journal_mode=WAL`；
* `PRAGMA foreign_keys=ON`。

在事务处理上，采用统一上下文管理器实现：

* 正常执行完成后提交事务；
* 出现异常时回滚事务；
* 最终释放连接资源。

该设计有利于保证数据库操作的一致性和稳定性。

## 9. 启动初始化与异常恢复机制

系统启动时执行 `init_db()`，主要完成以下两项工作：

1. 执行建表及建索引脚本，确保数据库结构存在；
2. 将系统上次异常退出前处于 `pending` 或 `running` 状态的任务统一标记为 `failed`，并写入错误信息 `Server restarted`。

该机制可确保系统在异常关闭或服务重启后，数据库中的任务状态与实际运行状态保持一致，避免前端展示“僵尸任务”或误判任务仍在执行。

## 10. 核心业务操作设计

根据设计草案，数据库需要支撑以下典型操作：

### 10.1 任务列表查询

用于左侧边栏展示历史任务，查询任务基础信息及其目标数量，并按创建时间倒序返回最近任务。

### 10.2 任务详情查询

用于详情页一次性加载任务基本信息、所有扫描目标、每个目标的阶段列表以及漏洞结果，支撑完整任务回显。

### 10.3 创建任务

创建任务时，按照以下顺序写入数据：

1. 插入 `tasks`；
2. 批量插入 `task_targets`；
3. 为每个目标预生成对应的 `task_stages`。

### 10.4 更新阶段状态

当后台解析日志发现阶段开始、完成或异常时，更新 `task_stages` 表中的 `status`、`output`、`updated_at` 字段。

### 10.5 存储漏洞结果

在目标扫描完成后，将解析出的漏洞结果逐条写入 `vulnerabilities` 表。

### 10.6 完成目标

当一个目标全部扫描结束后，更新 `task_targets`，写入：

* `status='completed'`
* `score`
* `readme`
* `ended_at`。

### 10.7 完成任务

当任务全部目标执行完毕后，更新 `tasks`，写入：

* `status='completed'`
* `completed_at`。

## 11. 扫描监控线程与数据库写入流程

系统中的 `monitor_task` 后台线程负责监听扫描日志并驱动数据库状态更新，其数据库写入流程如下：

1. 对新增日志行运行 `LogParser` 解析；
2. 解析到阶段开始事件时，更新阶段状态为 `running`；
3. 解析到阶段完成事件时，更新阶段状态为 `completed`，同时写入阶段输出；
4. 当目标完成时：

   * 插入漏洞结果到 `vulnerabilities`；
   * 更新 `task_targets` 的完成状态、评分及报告；
   * 更新 `tasks.current_target_idx`；
5. 当扫描进程退出时，更新 `tasks` 的最终状态和完成时间；
6. 每次写数据库后，同时向 SSE 队列推送事件，通知前端刷新。

这一机制实现了“日志驱动状态同步、数据库持久化、SSE 实时通知”三者联动。

## 12. SSE 实时流与数据库协同设计

为支持前端实时查看扫描进度，系统采用 SSE（Server-Sent Events）机制。其核心设计如下：

* 后端维护 `asyncio.Queue` 作为每个任务的实时事件队列；
* 前端建立 SSE 连接后，服务端首先从数据库读取任务完整状态并发送 `init` 事件；
* 后续扫描过程中的状态变更由 `monitor_task` 写数据库后同步推送到队列中；
* 若前端中途断线重连，可再次从数据库恢复最新完整状态，避免事件丢失。

这种设计使数据库不仅承担持久化职责，也成为前端断线恢复和状态重建的权威数据源。

## 13. 安全性与可维护性考虑

从当前设计看，数据库层已经考虑以下安全与维护因素：

1. 开启外键约束，防止无效引用数据产生；
2. 使用参数化 SQL，规避拼接型注入风险；
3. 启用 WAL 模式，增强并发读写体验；
4. 使用快照字段保留历史任务上下文，避免配置变更影响历史展示；
5. 引入启动恢复逻辑，减少异常重启带来的状态不一致问题。 

需要注意的是，当前方案中 `api_key` 以明文方式保存在本地 SQLite 中，这适用于本地工具场景，但若后续演进为多人共享或服务端部署模式，建议增加加密存储、密钥托管或环境变量隔离机制。该“本地明文存储”设定来自原始设计说明。

## 14. 后续扩展建议

结合现有设计，数据库未来可考虑以下扩展方向：

* 增加用户表与权限体系，支持多用户任务隔离；
* 增加任务标签、项目分组字段，提升任务组织能力；
* 将 `stage_ids` 从 JSON 文本拆分为关系表，增强查询能力；
* 增加漏洞去重、确认状态、修复状态等字段，支持漏洞闭环管理；
* 对 `api_key` 等敏感字段增加加密存储能力；
* 增加审计日志表，记录关键数据库操作历史。

以上为在现有设计基础上的合理扩展建议，不属于原始设计草案中的既有定义。当前正式数据库结构仍以前述五张核心表为准。

本数据库设计围绕“任务—目标—阶段—漏洞”这一主线建立了较为完整的数据模型，能够满足 MCP Scan 安全扫描平台在任务管理、阶段追踪、结果存储和前端实时展示方面的核心需求。整体方案结构清晰、关系明确、易于落地，适合作为当前版本系统的持久化基础。
